# 《百万美金》QQ 官方 Bot 开发实现设计

> 文档版本：v1.3.3
>
> 规则基线：2016 年初版
>
> 当前状态：设计已冻结；v1.5.0 已实现核心玩法，赃物牌组于 v1.5.0 完成逐张核验（见第 4.3 节与 `loot-deck-verification.md`）

本文档把桌游规则和 QQ 官方机器人能力转换为可直接开发、测试和审查的实现约定。规则事实以[完整中文规则](./million-of-dollars-rules-zh.md)为准；QQ 消息结构以[QQ 官方 Bot 开发说明](./qqofficial-bot-development.md)为准。

文中的“必须”“不得”是实现约束。若代码与本文冲突，应先更新设计及测试，再修改实现。

## 1. 已冻结的产品决策

- 支持 3～8 人和最多 8 回合，采用 2016 初版角色及结算顺序。
- 房间以 `platform_id + group_openid` 隔离，玩家以 `member_openid` 标识。
- 首版只提供 QQOfficial 群聊交互；其他平台不得误进入 QQ 专属发送逻辑。
- QQ 中所有可执行按钮使用 `action.type = 2`。
- 选角、告密人指定等服务端动作使用不透明 HMAC 令牌，按钮参数不能暴露真实动作。
- 谈判完全由玩家在 QQ 群内自行完成。插件不理解谈判内容，也不保存报价、接受或合约。
- “转账”和“退出”是两个独立原子操作：转账不会导致退出，退出不会附带转账。
- 威胁牌不使用 C2C。持牌人收到仅自己可用的目标按钮，点击后在自己的输入框查看明文身份，并自行放弃发送。
- 不实现可逆加密，不把 `member_openid` 当作秘密。

## 2. 平台交互边界

### 2.1 身份与房间

QQOfficial 群消息必须从原始事件的可信字段读取：

| 业务字段 | QQ 字段 | 用途 |
| --- | --- | --- |
| `platform_id` | AstrBot 平台实例 ID | 隔离不同 Bot 实例 |
| `group_openid` | `raw_message.group_openid` | 隔离群房间 |
| `member_openid` | `raw_message.author.member_openid` | 玩家身份和按钮权限 |
| `message_id` | `raw_message.id`，其次 `message_obj.message_id` | 幂等键和被动回复 |

不得从按钮文本、昵称或用户输入取得操作者身份。收到按钮插入的指令后，应用层必须再次用事件发送者校验权限。

### 2.2 type=2 按钮

普通按钮的最小结构：

```json
{
  "id": "mod_action_short_id",
  "render_data": {
    "label": "显示文字",
    "visited_label": "已提交",
    "style": 1
  },
  "action": {
    "type": 2,
    "permission": {
      "type": 0,
      "specify_user_ids": ["目标 member_openid"]
    },
    "data": "百万美金操作 <HMAC令牌>",
    "reply": true,
    "enter": false,
    "unsupport_tips": "当前客户端不支持该按钮"
  }
}
```

秘密动作统一使用 `visited_label = "已提交"`，不得把已选角色写进 `visited_label`。

公开菜单可以使用 `permission.type = 2`。公开操作必须同时提供纯文本指令；秘密选角发送失败时只能提示重试，不得降级为明文角色指令。

### 2.3 被动回复

由用户消息触发的按钮优先使用被动回复：

- 有 `msg_id` 时写入 `msg_id`；
- 否则有交互事件 ID 时写入 `event_id`；
- 同时提供本次回复的 `msg_seq`；
- API 失败时记录不含秘密的错误，并返回纯文本提示或保留原状态重试。

## 3. 模块边界

建议目录：

```text
astrbot_plugin_millionofdollars/
├── main.py                 # 插件注册和薄命令路由
├── game/
│   ├── models.py           # 枚举、快照数据结构及序列化
│   ├── rules.py            # 纯规则函数
│   ├── tokens.py           # HMAC 生成和枚举匹配
│   ├── repository.py       # SQLite、密钥和事务
│   ├── service.py          # 状态机、锁、幂等和用例编排
│   └── qqofficial.py       # 事件字段、keyboard 和发送适配
└── tests/
    ├── test_rules.py
    ├── test_tokens.py
    ├── test_service.py
    ├── test_repository.py
    └── test_qqofficial.py
```

依赖方向只能是：

```text
main → service → rules/models
              → repository
main → qqofficial → service DTO
```

`rules.py` 不得导入 AstrBot、botpy、sqlite3 或网络组件。QQ 适配层不得直接修改游戏快照。

## 4. 领域模型

### 4.1 枚举

```python
class Phase(StrEnum):
    LOBBY = "lobby"
    ROLE_SELECTION = "role_selection"
    NEGOTIATION = "negotiation"
    SNITCH_SELECTION = "snitch_selection"
    RESOLVING = "resolving"
    ROUND_END = "round_end"
    GAME_OVER = "game_over"

class Role(StrEnum):
    DRIVER = "driver"
    BRUTE = "brute"
    CROOK = "crook"
    SNITCH = "snitch"
    MASTERMIND = "mastermind"
```

金额一律用整数“百万美元”保存：初始现金为 `5`，即时胜利线为 `20`，不得使用浮点数。

### 4.2 玩家与人物槽位

每名玩家保存：

- `member_openid`、显示名称、加入顺序；
- `cash`、`threat_cards`、`action_generation`；
- 本轮是否准备；
- 一个或两个 `CharacterSlot`。

人物槽位保存：

- 稳定的 `slot_id`；
- 秘密角色；
- `ante_total`、玩家实际支付额和储备区补足额；
- `active`、`eliminated`、`ante_returned`；
- 角色是否已公开。

4～8 人局每位玩家一个槽位。3 人局每位玩家两个槽位，因此退出按钮必须指向具体槽位；玩家可以退出一个或两个角色。准备是玩家级操作：只要玩家仍有活动槽位，就需要准备一次。

### 4.3 赃物牌

```python
@dataclass(frozen=True)
class LootCard:
    card_id: str
    amount: int
    ante: int
    bonus_role: Role | None
```

牌组必须是 10 个经过原版资料逐张核验的常量，开局用安全随机源无放回抽取 8 张。

> v1.5.0 已完成核验：10 张牌面取自实物牌截图，方法与结果见
> [`loot-deck-verification.md`](./loot-deck-verification.md)。规则正文只给出了金额和保证金范围，开发时不得凭范围臆造 10 张牌面；录入牌组的提交必须附逐张核验测试或来源截图索引。

### 4.4 游戏快照

快照至少包含：

- schema 版本、`game_uuid`、房间键；
- 阶段、回合号、首领索引和玩家顺序；
- 8 张本局赃物牌及当前牌；
- 玩家、人物槽位、公开角色计数和被隐藏角色；
- 谈判开始时间；
- 告密人待选择者和合法目标；
- 胜者列表及最近一次公开结果。

秘密角色映射可以进入数据库快照，但不得进入公开回复或常规日志。

## 5. 状态机

```text
LOBBY
  → ROLE_SELECTION
  → NEGOTIATION
  → SNITCH_SELECTION（仅唯一告密人需要指定时）
  → RESOLVING
  → ROUND_END
  → ROLE_SELECTION / GAME_OVER
```

### 5.1 大厅

1. `创建`：当前群无未结束房间时创建，发送者加入并成为首领。
2. `加入`：仅 LOBBY 可用；拒绝重复加入和第 9 人。
3. `开始`：仅首领可用，人数必须为 3～8。
4. 开局生成 `game_uuid`，抽取 8 张赃物牌并进入第一轮。

### 5.2 选角

角色配置：

| 人数 | 可选角色 | 每人选择数 |
| --- | --- | --- |
| 3 | 五种全部 | 2，且不能相同 |
| 4 | 司机、暴徒、恶棍 | 1 |
| 5～6 | 再加告密人 | 1 |
| 7～8 | 再加谋士 | 1 |

每名玩家单独收到指定用户按钮。3 人局第一次成功选择后递增该玩家的 `action_generation`，重新生成排除首次角色的第二组按钮。

所有人物槽位选定后：

1. 收取当前赃物牌要求的保证金；
2. 将所有已选角色组成列表并安全洗牌；
3. 随机选一个槽位作为隐藏角色；
4. 只公开其余角色的计数，不公开玩家映射；
5. 记录谈判开始时间并进入 NEGOTIATION。

玩家现金不足时，按规则由储备区补齐保证金。实现必须分别记录玩家支付额和储备区补足额；退还保证金时按原版规则解释退回完整保证金。此行为必须有独立测试，避免结算时重复扣款或退款。

### 5.3 QQ 群谈判

插件不提供报价对象、报价金额、接受或拒绝状态。玩家直接在 QQ 群里交流。

插件只处理以下独立操作：

- `转账`：选择收款人后选择金额，最终按钮一次性执行资金转移；
- `退出`：4～8 人局退出唯一槽位；3 人局选择退出某个活动槽位；
- `准备` / `取消准备`；
- `强制抢劫`：谈判开始 60 秒后仅当前首领可用。

转账与退出之间没有自动关联：

```text
转账成功 → 只改变付款人和收款人的现金，并清空全部准备
退出成功 → 只退出指定人物槽位并退还其保证金
```

转账金额必须是正整数百万美元，不得向自己转账，不得超过付款人现金。目标选择只生成下一层金额按钮，不改资金；金额按钮携带目标和金额对应的 HMAC 动作，成功时在同一数据库事务中扣款和入账。

已退出的槽位不能再执行选角、转账、准备或角色动作。插件无法也不会阻止玩家继续发送普通群消息。

仍有活动槽位的玩家全部准备后立即结算。任何成功转账或其他谈判期资金变化都清空准备状态。

### 5.4 抢劫与告密人

结算函数接收不可变快照并返回新快照和公开事件列表，顺序固定：

1. 告密人；
2. 暴徒；
3. 司机；
4. 恶棍；
5. 谋士；
6. 告密人指定角色。

多个同角色活动槽位碰撞时全部淘汰。暴徒无论碰撞或被告密人指定，都退还保证金；其他被淘汰角色失去保证金。

唯一告密人先收回保证金。若存在可指定的已公开角色，进入 SNITCH_SELECTION，只向该告密人发送合法目标 HMAC 按钮；选择完成后继续 RESOLVING。若无合法目标，直接继续。

若最终只剩告密人，该玩家损失 300 万美元并被淘汰，本轮跳过分赃；现金不得降到零以下，实际扣除上限为现有现金。

### 5.5 分赃

必须按以下顺序执行，不得交换：

1. 活动谋士使赃物金额增加 2；
2. 按活动人物槽位数量平均分配，向下取整；
3. 每个获得份额的槽位向唯一活动司机支付 1；
4. 唯一活动恶棍从唯一活动暴徒处夺取 2；
5. 当前赃物牌的活动奖励角色获得 1。

3 人局按人物槽位分份，同一玩家可以获得两份。玩家自己的角色之间付款仍生成领域事件，但净资产可以不变。所有付款均以实际可支付金额为上限，不能产生负数。

分赃后立即检查：

- 一名或多名玩家现金至少为 20：最高者获胜；同额则共同获胜；
- 否则第 8 回合结束：现金最高者获胜，同额共同获胜；
- 否则轮换首领，清理本轮状态并进入下一轮 ROLE_SELECTION。

## 6. HMAC 动作协议

### 6.1 密钥

首次运行：

```python
server_secret = secrets.token_bytes(32)
```

密钥写入 AstrBot 为插件分配的数据目录，采用仅当前进程账户可读的文件权限；不得写进源码目录、配置、日志或安装包。重启必须复用同一密钥。

### 6.2 规范载荷

使用 UTF-8 JSON，固定字段名、固定顺序、无多余空格：

```json
{
  "v": 1,
  "game": "<game_uuid>",
  "group": "<group_openid>",
  "round": 1,
  "phase": "role_selection",
  "generation": 3,
  "actor": "<member_openid>",
  "action": "choose_role",
  "params": {"role": "driver"},
  "nonce": "<base64url>"
}
```

生成：

```python
nonce = secrets.token_bytes(16)
mac = hmac.new(server_secret, canonical_payload, hashlib.sha256).digest()[:16]
token = base64.urlsafe_b64encode(nonce + mac).rstrip(b"=").decode("ascii")
```

外部令牌固定为 32 字节编码后的 43 个 base64url 字符。日志最多记录前 6 个字符。

### 6.3 匹配而非反解

令牌只携带 `nonce + mac`，不携带可解析的动作。收到 `百万美金操作 <token>` 后：

1. 以群键取得房间锁；
2. 以事件发送者取得玩家，不读取按钮中的用户参数；
3. 验证令牌长度和 base64url 格式；
4. 从令牌取出 nonce；
5. 根据当前游戏、阶段和该玩家状态枚举所有合法动作；
6. 为每个候选动作结合收到的 nonce 重算 HMAC；
7. 用 `hmac.compare_digest` 匹配；
8. 无唯一匹配时拒绝，且不泄露候选列表。

成功动作或主动刷新按钮后，只递增该玩家的 `action_generation`。其他玩家的按钮不失效。

## 7. 威胁牌的特殊按钮

威胁牌是唯一不使用 HMAC 密文动作的按钮。原因是当前 QQOfficial type=2 按钮没有插件可依赖的私密回调结果，而用户选择在本地输入框查看。

流程：

1. 持牌人请求使用威胁牌；
2. 服务端在房间锁内确认其至少有一张牌，并冻结一次发放请求；
3. 为每个可查看的活动人物槽位构造一个仅持牌人可用的按钮；
4. 按钮标签显示目标玩家或人物槽位，`action.data` 直接包含该目标真实身份；
5. `enter = false`，点击只把文字放进持牌人的输入框；
6. QQ API 确认完整按钮组发送成功后，事务内扣除一张威胁牌并完成幂等记录；
7. 发送失败则取消冻结，不扣牌。

示例：

```json
{
  "render_data": {
    "label": "查看 小明",
    "visited_label": "已查看",
    "style": 1
  },
  "action": {
    "type": 2,
    "permission": {
      "type": 0,
      "specify_user_ids": ["持牌人 member_openid"]
    },
    "data": "查看结果：小明本轮身份是暴徒。请勿发送此内容。",
    "reply": false,
    "enter": false
  }
}
```

3 人局目标必须精确到人物槽位，例如“小明·人物 1”。

### 7.1 明确的保密边界

此方案只防止普通 QQ 客户端中的其他玩家点击按钮。身份明文会进入发给客户端的 keyboard payload，因此：

- 不抵御抓包、改造客户端、平台日志、截图或持牌人主动发送；
- 不具备 HMAC 选角按钮的服务端密码学保密；
- 玩家若误按发送，机器人不能保证撤回；
- 文档和界面必须提示“点击查看后不要发送”。

若未来需要强保密，应改为可信私聊通道或平台支持的私密交互，而不是继续扩展此明文按钮方案。

## 8. 持久化与事务

使用标准库 `sqlite3`，不新增依赖。建议表：

```sql
CREATE TABLE meta (
  key TEXT PRIMARY KEY,
  value BLOB NOT NULL
);

CREATE TABLE games (
  platform_id TEXT NOT NULL,
  group_openid TEXT NOT NULL,
  game_uuid TEXT NOT NULL,
  status TEXT NOT NULL,
  snapshot_json TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (platform_id, group_openid)
);

CREATE TABLE processed_messages (
  platform_id TEXT NOT NULL,
  group_openid TEXT NOT NULL,
  message_id TEXT NOT NULL,
  result_json TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (platform_id, group_openid, message_id)
);
```

`meta` 保存 schema 版本；HMAC 密钥优先保存为数据目录的独立权限文件，不放入快照。快照 JSON 必须有显式 schema 版本和严格反序列化校验。

每个房间有独立 `asyncio.Lock`。状态动作的顺序：

1. 获取房间锁；
2. 开启 SQLite 事务；
3. 查询 `processed_messages`，命中则返回原结果；
4. 读取并校验最新快照；
5. 执行动作；
6. 更新快照及操作者 `action_generation`；
7. 写入消息结果；
8. 提交事务后回复。

异常必须回滚。不得在一个房间动作中取得另一个房间的锁。

QQ 发送属于外部副作用，无法与 SQLite 实现真正的单事务原子性。威胁牌采用“冻结发放请求→发送→成功后扣牌”的补偿流程，并以原始 `message_id` 保证重复请求返回同一结果。崩溃恢复时遇到未完成发放记录，应保留威胁牌并要求玩家重新请求，文档承认极端情况下可能重复看到同一身份，但不得无消息扣牌。

## 9. 指令与按钮流程

公开文本入口建议统一为：

```text
百万美金 创建
百万美金 加入
百万美金 开始
百万美金 状态
百万美金 菜单
百万美金 转账
百万美金 退出
百万美金 准备
百万美金 取消准备
百万美金 强制抢劫
百万美金 使用威胁牌
百万美金 操作 <HMAC令牌>
```

其中“转账”先返回目标按钮，再返回金额按钮；“退出”在 3 人局返回人物槽位按钮。最终改变状态的按钮均使用 HMAC，且任何参数都以服务端匹配结果为准。

公开指令可提供必要的文本参数回退，例如 `百万美金 转账 @目标 2`，但仍需按真实发送者、当前成员和余额校验。选角与告密人指定不得提供暴露角色参数的文本回退。

## 10. 日志与错误

允许记录：

```text
room=<platform/group>
game=<uuid前8位>
round=<n>
phase=<phase>
actor=<member_openid摘要>
action=<动作名>
result=<成功/拒绝原因类别>
token=<前6位>
```

不得记录：

- HMAC 密钥或完整令牌；
- 选角玩家—角色映射；
- 隐藏角色；
- 威胁牌按钮的完整 payload 或身份明文；
- SQLite 完整快照。

所有用户输入必须限制长度并校验类型。令牌畸形、旧阶段、越权、余额不足、重复退出等错误只返回必要说明，不返回合法动作枚举或签名材料。

## 11. 测试验收矩阵

### 11.1 令牌

- 同一候选动作连续生成两次令牌不同；
- 游戏、群、回合、阶段、玩家、参数或 `action_generation` 变化均无法匹配；
- 正确玩家可匹配，其他玩家、篡改令牌和旧按钮失败；
- 重放、重复 `message_id` 和并发点击最多成功一次；
- 密钥重启复用，仍处于相同状态的按钮可继续验证。

### 11.2 规则

- 3～8 人角色集合；
- 3 人双槽位、两次不同角色选择和单槽位退出；
- 隐藏一个角色且只公开计数；
- 五种角色的唯一、碰撞、告密人指定和暴徒保证金例外；
- 谋士、平均分配、司机、恶棍和牌面奖励的固定顺序；
- 仅剩告密人、20 点即时胜利、第 8 回合和并列胜利。

### 11.3 谈判

- 转账只改变双方现金，不退出；
- 退出只改变指定槽位并退保证金，不转账；
- 不存在报价、接受或组合动作状态；
- 成功转账清空准备；
- 非首领、未满 60 秒及旧阶段不能强制抢劫。

### 11.4 威胁牌

- 所有目标按钮仅持牌人的 `member_openid` 可用；
- `action.type = 2`、`enter = false`，data 含目标身份提示；
- 发送成功扣一张，失败不扣，重复消息不重复扣；
- 无 C2C 绑定依赖；
- 3 人局目标精确到人物槽位。

### 11.5 QQ 与恢复

- 被动回复的 `msg_id/event_id/msg_seq` 正确；
- 普通秘密按钮 data 只有 HMAC 指令且 `visited_label = "已提交"`；
- 公开菜单有纯文本回退；
- SQLite 重启恢复房间、玩家、回合、阶段、代次和已处理结果；
- 安装包不包含密钥、数据库、缓存或测试临时文件。

## 12. 开发顺序

1. 建立领域数据结构和纯规则测试；
2. 实现 HMAC 密钥、令牌和枚举匹配测试；
3. 实现 SQLite 仓储、迁移、幂等和恢复测试；
4. 实现房间服务、状态机、锁和事务；
5. 实现 QQOfficial 事件及 keyboard 适配；
6. 接入公开菜单和秘密选角；
7. 接入独立转账、独立退出、准备和超时；
8. 接入角色结算、分赃和胜利；
9. 接入威胁牌特殊按钮及发送补偿；

首个可玩版本不得在赃物牌常量尚未逐张核验、秘密按钮权限未真机验证或事务/幂等测试未通过时发布。

## 13. 实现补充约定

本节记录 v1.4.0 实现时对本文未明确之处的取舍。若后续要修改这些行为，应先更新本节与对应测试。

### 13.1 保证金退款口径

本文 5.2 要求“退回完整保证金”，但未说明现金不足时由储备区补齐的部分如何归属。
实现按原版实物流程解释：储备区把不足的钞票直接交给玩家，玩家把整笔保证金压在人物牌上，
因此退保证金时**玩家收回完整 `ante_total`**，储备区不回收 `reserve_paid`。

`player_paid` 与 `reserve_paid` 只用于记账与避免重复退款，不改变退款金额。
`refund_ante()` 通过 `ante_returned` 保证幂等，唯一暴徒被淘汰或被告密人指定时不会重复退款。
独立测试：`tests/test_rules.py::test_refund_ante_returns_the_full_ante_once`。

### 13.2 强制抢劫的效果

本文 5.3 只规定了“谈判开始 60 秒后仅当前首领可用”，没有规定效果。
实现按“首领推动讨论”的定位，把它定义为：

- 立即结束谈判阶段，仍在场的人物槽位直接进入抢劫结算；
- 每轮最多成功一次，结束后 `force_rob_used` 置位，进入下一轮时重置；
- 非谈判阶段、非首领、未满 60 秒一律拒绝。

### 13.3 退出也会清空准备

本文 5.3 规定“任何成功转账或其他谈判期资金变化都清空准备状态”。
退出会退还保证金，属于谈判期资金变化，因此 `leave_slot()` 同样清空全员准备状态。

### 13.4 按钮数量上限

QQOfficial keyboard 最多 5 行、每行 5 个按钮。公开菜单用 `ButtonSpec.row` 显式分行
（参考 `astrbot_plugin_buckshot_roulette` 的菜单：每行 2 个语义相关的按钮）；
未指定 `row` 时每 5 个按钮自动成一行。实现按 5 行、25 个按钮截断：

- 选角按钮最多 5 个；
- 转账金额按钮 1～25，现金超过 25 百万美元时玩家需要分次转账；
- 威胁牌目标按钮按 3 人局槽位数量生成，最多 8 个。

### 13.5 公开角色与告密人目标

公开角色计数在选角结束、收取保证金后计算（本文 5.2 第 4 步），
因此包含之后在谈判阶段退出的玩家。告密人的合法指定目标即该计数的键集合，
指定已经被淘汰或已经退出的角色不会产生新的淘汰。

### 13.6 威胁牌的使用时机

本文第 7 节说威胁牌“可在之后任意一轮的任意时刻使用”。
实现限定在 `NEGOTIATION` 阶段，因为只有该阶段同时存在活动人物槽位
（结算前），选角阶段尚未确定角色，结算阶段已经公开身份。

### 13.7 选角按钮的刷新

3 人局第一次成功选角后只递增该玩家的 `action_generation`，
并只向该玩家重新发送排除首次角色的第二组按钮；其他玩家的按钮不受影响。

### 13.8 命令与按钮的等价关系

所有公开按钮的 `action.data` 都等价于一条可手动输入的文本指令
（如 `百万美金 创建`）。秘密动作按钮使用 `百万美金 操作 <HMAC令牌>`，
不提供明文回退。文本入口与按钮共用同一套服务端校验。

### 13.9 规则卡图片与身份揭露卡图

产品要求：`百万美金 帮助` 输出规则卡图片；抢劫阶段身份揭露时用角色卡图片。

实现约定：

- 规则卡图片：`docs/sources/rule-cards/rule-card.jpg`，随帮助文本一起发送；
  文件缺失时只回复文字并提示管理员。
- 身份揭露图片：渲染本轮**中心牌堆**并合并成**一张**图片发送 —— 每个提交过角色的
  槽位一张牌，被随机隐藏的那张用**卡背**代替，其余为角色卡；超过 5 张自动换行。
- 卡片顺序每次随机打乱，避免固定顺序暗示玩家与角色的对应关系。
- 卡背位置也参与打乱，不暴露"哪一张被隐藏"。
- 谈判期退出的玩家，其角色牌仍匿名留在中央牌堆（牌堆不标注归属），因此也在图中。
- 进入 `SNITCH_SELECTION` 时不发送揭露图，留到本轮真正结算时与结算文本一起发送。
- 图片路径在 DTO 中使用相对插件根目录的形式，QQ 适配层解析为绝对路径后经
  AstrBot 消息链路发送；图片发送失败不影响文本与按钮。
- 合成使用 Pillow（AstrBot 既有依赖）；系统存在中文字体时自动在卡片下方加中文角色名，
  没有中文字体时只输出卡面。

### 13.10 房间管理（v1.7.0）

参考 `astrbot_plugin_buckshot_roulette` 的房间逻辑补充：

- `退出房间`：仅 `LOBBY` 阶段可用；最后一人退出即删除房间快照；首领退出时把首领
  转交给剩余的第一位玩家，并重排 `join_order`（实现里用首领 openid 重新定位
  `leader_index`，不依赖移除前后下标一致）。
- `关闭房间`：首领或 AstrBot 管理员可用，任意阶段都能删除房间快照。
- 人数计数统一由 `_room_size()` 生成（`x/8 人`），创建/加入/退出/状态/关闭回复都会带上。
- 所有指令入口最后都调用 `event.stop_event()` 与 `should_call_llm(True)`：
  AstrBot 仅在「插件调用过 `event.send`」或「事件被 stop」时跳过默认 LLM，
  本插件用 `post_group_message` 直发，必须显式终止事件。
- 无空格写法（`百万美金创建`）注册为命令别名，避免匹配不到过滤器而漏进 LLM。
